# Agent Note: 语音发送的新鲜度与控制状态

Status: implemented

## Problem

协议命令等待网络回复时，编码包会在 actor 的有界队列里积压。队列有容量限制仍可能把过时的声音连续发出；来自采集线程的延迟状态也可能覆盖用户刚提交的 PTT 意图。

## Decision

actor 持有 mute/deafen/PTT 的控制状态，采集线程只报告设备就绪情况。编码包携带单调时钟时间，发送前核对当前连接、频道、codec、采集状态和发送开关。超过 100ms 的排队包被丢弃，控制状态或频道变化使此前产生的包失效。

闭麦、聋听或松开 PTT 时立即清除本端说话状态；排队的说话事件不能重新点亮已关闭的发送开关。协议出口继续由 actor 独占，采集线程不持有 Client。

线程归属与设备生命周期仍由[双线程全双工语音](../../implemented/architecture/2026-10-18-full-duplex-audio.md)规定；电平发布由[实时语音电平](../../implemented/architecture/2026-10-29-realtime-voice-levels.md)规定。发送链路的当前参数见[音频文档](../../../../docs/audio.md)。

## Alternatives considered

**只依赖有界队列与采集端静音**。队列中的包已经越过采集端，网络等待结束后仍可发出，容量限制不能保证实时性或闭麦语义。

**在音频线程直接发协议包**。这会绕过 Client 的串行执行要求，并让设备线程承担网络阻塞。

**等待全部积压声音发送完成**。完整性优先会拉长交谈延迟；实时语音采用丢弃过期包的策略。

## Consequences

网络阻塞超过阈值会造成语音空隙，避免把等待时间累加到后续交谈。100ms 约容纳五个编码帧，属于可调整的排队上限，不能当作端到端延迟承诺。

回归测试覆盖过期包、控制切换前的包、关闭的发送开关，以及采集状态事件保留 PTT 意图。
