# 通用编码反面准则

本文定义仓库通用的编码原则、错误处理、代码复用与类型系统反面模式。

## 最高原则

- 第一性原理：从原始需求出发，动机不清立刻停，路径非最优直接纠正。
- 如无必要，勿增实体；回复与文档用中文，末尾不追加无关建议，不给用户增加选择负担。
- Actions over filler：直接做事，不绕弯；凡需表态处选定立场并捍卫，不依赖「看情况」。
- 先阅读所有相关文件，了解全部需求后再编辑；结论先行，不寒暄。
- 不评价问题、不道歉、不揣测后续意图、不评价自己的改动；只修改与测试代码。
- 简洁性高于一切：只写必要代码，丑陋冗余是严重错误；最简可用方案，不过度设计，不添加推测性功能，不说「你可能还需要……」。

## FAILFAST

- 错误做法：大量兼容、防御性、补丁式代码；对错误做表面消化后继续；吞异常、写兜底默认值掩盖失败。
- 正确做法：不为虚构分支打补丁，错误按原样向调用方暴露；错误用 `thiserror`，每层一个错误类型，跨层用 `#[from]` 转换，不 `unwrap`；继续前进前先修复错误，不跳过失败。

## YAGNI

- 错误做法：保留会产生警告或无人使用的「未来功能」代码；写没人调用的抽象、TODO 占位、「以后可能用得上」的代码。
- 正确做法：不预留推测性能力；需要时从 Git 历史找回。

## DRY

- 错误做法：两处重复就急着抽公共抽象。
- 正确做法：三处相似代码胜过一次过早抽象；单次使用的操作不做抽象。

## 警告压制处置

- 错误做法：任何形式的表面抑制或欺骗性消除——编译器属性（如 `#[allow(...)]`）、Dart 的 `// ignore:`、注释禁用、通过无意义的变量读取、日志打印、空操作绕过警告（如给未用变量加下划线）。
- 正确做法：从根因分析警告成因，修正设计彻底消除：实现或删除冗余代码、修复类型问题、重构逻辑。

## 类型安全优先

- 错误做法：用原始 JSON 值与字符串类型数据承载结构化信息，靠人肉校验。
- 正确做法：优先选择强类型结构体，让编译器校验结构。

## 时序不承载正确性

正确性必须来自具名调用点、显式状态流与静态生命周期，绝不能依赖异步回调或事件落在循环队列的哪个微小时间缝隙。用延迟、微任务等待某项工作完成，是在与系统的其余部分并发竞态。

- **错误做法（Dart / Flutter）**：
  - 使用 `Future.delayed(Duration(...))` 等待渲染树构建完成或状态刷新；
  - 使用 `scheduleMicrotask` 或 `Future.microtask` 规避“在 build 期间更新状态”的告警，假装时序成立；
  - 使用 `addPostFrameCallback` 掩盖组件生命周期与 Riverpod 状态通知的竞态；
  - 依赖多个未受控异步 Future 的完成先后顺序。
- **正确做法（Dart / Flutter）**：
  - 由 `SessionController` / Riverpod 状态机显式驱动状态演进；
  - 将操作放到用户交互的事件回调中执行，或通过监听器（`ref.listen`）在确定性生命周期点触发；
  - 瞬时通知走 `NoticeCenter`，不在 widget 内部做定时重试或轮询检查。
- **错误做法（Rust）**：
  - 在非测试代码中用 `std::thread::sleep`、`tokio::time::sleep` 猜测并等待其他线程、网络或 Actor 准备就绪；
  - 在音频线程回调中做延时或等待。
- **正确做法（Rust）**：
  - 线程同步与工作调度依赖 Actor MPSC 信道、显式状态机、无锁环形缓冲区或 `tokio::sync::oneshot` / `watch`；
  - 等待一个状态转换必须显式监听该事件或通知，严禁无依据的定时轮询。
