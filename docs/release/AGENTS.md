# AGENTS.md — 发版日志

本目录存放每个版本的 Release 正文，一篇一版：`<tag>.md`，文件名与 git tag 完全一致（tag `v0.2.0` 对应 `v0.2.0.md`）。发版日志面向**终端用户**，同时作为 GitHub Release 正文与应用内更新弹窗内容。写新版本时与该版改动一起提交。

发布流程：tag 推送后 `.github/workflows/release.yml` 构建七平台产物，并直接以本目录的 `<tag>.md` 作为 GitHub Release 正文、以 `Release v<版本>` 作为 Release 标题公开发布（若带 `-beta`、`-rc`、`-dev` 自动标记为预发布）。文件缺失或首行格式不符则终止发布，操作步骤见 [.agents/skills/fls-release-log/SKILL.md](../../.agents/skills/fls-release-log/SKILL.md)。流程与发布矩阵见 [../ci-cd.md](../ci-cd.md)。

## 生命周期

日志在发版前写下，与该版的改动一起提交；tag 打完之后冻结，下一版的改动进下一篇。只有事实写错时才回头修改已发布的日志，并在提交信息里说明改的是哪一处事实。

## 文件格式

第一行是 `# <版本> (<发布日期>): <主要更新简述>`：版本是 tag 去掉前缀 `v`，日期取发版当天（回填旧版本时取该 tag 的日期），简述概括这一版的主线，例如 `# 0.2.0 (2026-10-25): 语音体验与画面共享`。随后一段总述（一到三句，概括本版对用户最主要的变化与涉及平台），然后是分类条目、可选的「升级注意」与「贡献者」。

分类小节只用这四个名称，按此顺序出现，且只写本版实际有内容的分类：

```
## 新增
## 修复
## 优化
## 其他
```

归类的判据是终端用户视角：`新增` 收用户可用的新功能与新入口，`修复` 收用户可感知的缺陷与安全修复，`优化` 收体验、性能、音画质量与稳定性提升，`其他` 仅用于简要收拢非功能维护（如平台支持、打包与依赖更新），不逐条罗列内部重构、测试或文档改动。

之后可以出现：

```
## 升级注意
## 贡献者
```

写法规则：

- 每条一句话，直接写**用户看到的结果或解决的问题**，不抄提交主题原文。
- 不写代码内部符号与实现细节：不出现函数名、类名、模块路径、内部事件名、FFI 接口名、UI 控件名或内部数据结构，也不解释底层实现机制；仅在用户需要直接识别或操作时写出界面名称、快捷键、系统权限或外部配置项名称。
- 首行的简述是这一版主线的几个字概括，语气与总述第一句一致，不重复总述第一句；没有单一主线时取最贴近的一条（如「多项修复与维护」）。
- 首行的版本必须等于 tag 去掉前缀 `v`，日期写成 `YYYY-MM-DD`；`release.yml` 按这三段校验首行，不合格式即终止发布。
- 能确定来源时在句末附 `（#<PR 号>）`，便于溯源。
- `## 升级注意` 只在终端用户需要动手时出现（如重新授予权限、修改设置、卸载重装等），写明谁受影响、要做什么。整节没有内容就删掉整节，不写「无」。
- `## 贡献者` 列出本版的人类贡献者 `@handle`，机器人账号不计。
- 禁用 AI 套话、工程黑话与生硬书面语：不要以「本版本引入……」「本次更新带来了……」「客户端新增/重点改进……」开头，也不要写「无需用户额外操作」「所有改动向后兼容」等无信息量的兜底安抚；总述直接说这一版给用户带来了什么变化。避免「补齐」「接线」「落盘」「承接」「钻取」「收拢」「退避」「降载」「兜底」「回显」「遥测」「链路」「泛洪」「变通」「规整」「解耦」等内部工程词或怪异表达，以及「全面」「深度」「显著」等空洞修饰和破折号连接句子，改用自然直白的日常动词（如「支持」「新增」「修复」「改进」「改为」）直接说清楚结果与影响范围。
- 禁 emoji；一段一物理行；不写内部行号与 `file:line` 引用；不写这一版之外的计划或承诺。

模板：

```markdown
# <版本> (<发布日期>): <主要更新简述>

<一到三句总述：这一版对用户最主要的变化与涉及平台。>

## 修复

- <从用户视角说明修复的问题或恢复的行为>（#<PR 号>）

## 优化

- <用户可感知的体验、性能或稳定性改善>（#<PR 号>）

## 贡献者

- @<handle>
```
